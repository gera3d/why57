# Daily AI Workflow

Run one known-useful AI method on one current job. The output is an operating card and a reviewable work product, not an unattended system for managing the day.

Keep reusable method separate from current context:

- **Method:** trigger, approved skill, input boundary, output format, review gate, stop condition, and feedback process.
- **Current job:** the selected notes, relationship facts, or project facts authorized for this run.

## 1. Confirm the recipe is ready for daily use

Use this skill only when the owner has already tested the underlying recipe on a comparable, bounded task and approved its current method.

Before running, collect or confirm this operating card:

| Field | Record |
| --- | --- |
| Trigger | The specific work event that starts this run. |
| Approved skill | The one approved method or skill to use. Do not load unrelated tools. |
| Current inputs | Named, current, authorized materials only. |
| Expected output | The reviewable brief, ranked list, or draft package. |
| Review gate | The owner's required factual and judgment check. |
| Stop condition | A missing fact, unsuitable request, authority boundary, or stale input that ends the run. |
| Feedback note | What the owner changed and a proposed method update, if any. |

Stop and ask the owner to repair the card when a field is missing. A broad aspiration such as "make my workday better" is not a daily trigger.

## 2. Gather only the authorized, current inputs

Use the smallest set that supports the output. Label every input with a source, date, and reason it belongs in this run. Keep verified facts distinct from inferences and unknowns.

Use these bounded starting patterns:

| Daily job | Authorized input | Reviewable output | Owner's required check |
| --- | --- | --- | --- |
| Turn one selected meeting into a decision brief | Approved notes from one meeting, stated decisions, and the current project context | Decision brief with decisions, owners, open questions, and a source list | Confirm commitments, owners, dates, and missing context. |
| Produce a daily relationship review | A small, current list of relationship facts the owner is authorized to use | Ranked follow-ups, watch items, and questions—not sent messages | Check relationship nuance, privacy, and whether each next step is appropriate. |
| Draft a recurring client update | Verified project facts, approved milestones, known risks, and the reporting period | Draft update with source-backed claims and gaps flagged | Verify every client-facing fact, promise, date, and tone. |

Exclude full inboxes, private archives, credentials, unrelated tools, stale summaries, inferred facts, unattended messaging, purchases, scheduling, account changes, and any task requiring external execution.

## 3. Run the reviewable first pass

For every run, produce an **evidence and review packet** before drafting externally consequential language:

1. Restate the operating card in a compact table.
2. List inputs used with source labels and dates.
3. Separate verified facts, reasonable inferences, and unknowns.
4. Produce the requested brief, ranking, or draft outline in the specified format.
5. List the owner's review checks and the exact stop condition.
6. Ask: **“Approve this evidence and scope before I draft or take any consequential action?”**

Do not draft the recurring client update or any other external-facing copy until the owner explicitly approves the evidence and scope. Do not send, schedule, buy, submit, publish, modify accounts, or take other external action even after approval; provide a reviewable draft only.

## 4. Apply the taste test

Before the owner uses the output, test it against these questions:

- Does every material claim map to a current input, or is it marked as an inference or unknown?
- Did the output answer the operating card's expected outcome without expanding scope?
- Would the owner know what to check, decide, or do next?
- Did the run avoid unnecessary data and tools?
- Is the work useful enough to keep, rather than merely a record of AI activity?

Stop when a material fact cannot be verified, the input is stale or unauthorized, the requested step requires owner authority, or the output needs more interpretation than it saves. Record the stop reason plainly.

## 5. Capture feedback without silently changing the method

End each run with this feedback note:

| Keep | Change | Why | Proposed method update | Owner approval |
| --- | --- | --- | --- | --- |
| [what worked] | [what created friction] | [specific evidence] | [exact wording or field change] | Pending / approved / declined |

Treat a one-off correction as feedback about that run. Treat it as a method change only after the owner explicitly approves the proposed update. Never turn a prompt adjustment into a permanent instruction by default.

## 6. Hold the authority boundary

- Do not load every available tool, broad archive, or unrelated source.
- Do not turn one anomalous run into a standing rule.
- Do not hide owner approval inside an automation step.
- Do not report drafts, suggestions, or review queues as completed actions.
- Do not measure activity counts as a substitute for a useful, verified output.
- Do not infer facts, revive stale information, or treat a draft as sent, scheduled, or approved.

Deliver the operating card, evidence and review packet, reviewable output, and feedback note. The owner controls method changes and every consequential action.
