# Proof Library

Turn approved project records into reusable, reviewable proof cards. This is a method, not preloaded client data, a testimonial generator, or an autonomous agent.

## 1. Set the use and approval boundary

Ask for one intended use:

- a credible response to a specific sales question;
- safe examples for a capability page; or
- a first case-study outline from approved records.

Ask the owner to provide only a selected, authorized set of project notes, launch records, feedback, outcome records, and prior approval notes. Record the source label or link, its date, its owner, and any use restriction before extracting a claim.

Reject or exclude:

- confidential or restricted client material;
- passwords, API keys, tokens, raw credentials, or private account exports;
- unapproved names, logos, screenshots, customer quotes, or contact details;
- a result with no supporting record; and
- evidence the owner cannot explain, date, or substantiate.

If permission, scope, date, or source is missing, mark the item **needs owner confirmation**. Do not turn it into a public-facing claim.

## 2. Build source-linked proof cards

Create one card per narrow, supportable fact. Keep the original source pointer with the card; do not replace it with a model summary.

Use this exact structure:

| Field | Record |
| --- | --- |
| Proof ID | Stable short identifier |
| Claim | The narrow fact supported by the record |
| Source | Owner-approved link, file name, or record ID plus a short locating note |
| Source date | Date on the record; otherwise `unknown` |
| Scope | Project, role, deliverable, audience, period, and relevant conditions |
| Evidence type | Project note / launch record / customer feedback / outcome record / approval note |
| Permission status | Internal only / owner-approved for named use / owner-approved anonymized use / needs owner confirmation / do not use |
| Allowed wording | The strongest truthful wording the source supports |
| Cannot claim | Unsupported outcome, broader capability, causation, client identity, or guarantee to exclude |
| Freshness | Current / dated but usable with date / stale—recheck before reuse |
| Review note | What the owner must verify or approve |

Write claims as observations, not promises. Preserve the difference between:

- **Delivered:** what was actually built, reviewed, launched, or documented.
- **Observed outcome:** what a dated source reports happened after the work.
- **Customer feedback:** whose opinion it is, with approval to quote or attribute.
- **Inference:** a possible interpretation that must stay labeled as an inference.

Do not convert a delivery fact into a result. Do not convert one client’s result into a general promise. Do not say the work caused an outcome when the source shows only that the outcome followed it.

## 3. Run the proof check

For every card, check these questions in order:

1. Can the owner open the cited source and find the fact?
2. Does the wording preserve the source’s scope, date, and conditions?
3. Does the permission status cover this exact use, including the client name, logo, quote, and screenshot if any?
4. Is the outcome measured, dated, and attributable enough to state as an observed result?
5. Would a reasonable reader take the wording as a broader promise, typical outcome, or causal claim? If so, narrow it or exclude it.

Flag and stop on metric inflation, credit for work the client performed, causal claims from correlation, stale proof, named-client disclosure without approval, and fabricated testimonials. Treat feedback as feedback, not proof of a universal result.

## 4. Return a reviewable library first

Return the proof-card table, then a short review queue:

| Proof ID | Proposed use | Status | Owner decision needed |
| --- | --- | --- | --- |
| PL-001 | Sales response / capability page / case-study outline | ready for owner review / needs owner confirmation / do not use | Approve wording, correct scope, approve anonymization, or remove |

Separate cards into:

- **Ready for owner review:** source, scope, date, and permission are clear.
- **Needs owner confirmation:** a material fact, date, permission, or causal interpretation is uncertain.
- **Do not use:** restricted, stale beyond reliable use, unsupported, or not approved for the requested channel.

Do not draft sales copy, a capability page, proposal language, a case study, testimonial, send, post, publish, or share anything until the owner approves the selected cards and the exact channel.

## 5. Use approved cards for one job

After the owner approves selected proof cards, create only the requested draft:

- **Sales response:** answer the buyer’s stated question with the approved card’s allowed wording and a source reference for internal review.
- **Capability page examples:** propose a short, anonymized or named example only at the approved permission level; retain the bounded scope.
- **First case-study outline:** draft `context → problem → work → approved evidence → owner-approved quote or result → limits/next step`. Leave missing evidence visibly unresolved.

Keep the source pointers in the review packet. Remove private source text and identifiers from the outward-facing draft unless permission explicitly covers them.

## Synthetic example

Label this example **synthetic**. It demonstrates the method and is not a client result.

| Field | Example |
| --- | --- |
| Claim | A scheduling portal launched with a public intake form and status dashboard. |
| Source | `Launch checklist, 2026-07-14, section “go-live acceptance”` |
| Scope | One client portal; launch date only; no adoption or revenue finding. |
| Permission status | Owner-approved anonymized use. |
| Allowed wording | “Launched a public intake and status portal for one client.” |
| Cannot claim | “Increased signups,” “reduced support volume,” “proved our portal process,” or a named-client reference. |

## 6. Preserve owner authority

| AI may do | Owner must do |
| --- | --- |
| Extract source-linked facts, identify uncertainty, suggest bounded wording, classify freshness, and prepare a draft for review. | Confirm source accuracy, approve client disclosure and wording, decide whether an inference is fair, approve any quote, and choose whether to send, publish, submit, or share. |

Do not access accounts beyond the owner’s selected material. Do not create testimonials, use client names or logos, represent customer opinions, change a CRM, send messages, post, publish, submit, buy, or change access.

## 7. Taste test before use

Approve a card only when a reviewer can answer yes to all of these:

- I can open the cited record and find the claim.
- The date, project scope, role, and permission status are clear.
- The allowed wording does not imply a broader result, typicality, causation, or guarantee.
- The selected channel is covered by the approval status.
- The draft states uncertainty or removes the card where evidence is incomplete.

If any answer is no, keep the card out of the draft and ask the owner for the missing approval or evidence.
