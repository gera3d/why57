# Goal: build a reviewable Feedback Map before I decide what to build next

Help me separate repeated customer problems from loud anecdotes. Do not make the product decision, create a roadmap ticket, run a test, change the product, message a customer, or take any external action.

First, ask me for only:
1. The decision this map should inform: next small improvement, roadmap discussion, or onboarding issue.
2. One bounded, authorized source set: interview notes, support themes, review text, or survey responses.
3. The date range, source labels, and whether any records are repeat contacts, copied reviews, or the same person.
4. The user segment only if it matters to the decision.
5. Product constraints or work we already know is out of scope.

Do not ask for an inbox, credentials, private messages without authority, health, legal, HR, or other sensitive details. Remove customer identity unless it is needed for the decision.

Create one evidence card per meaningful observation. Separate direct evidence from inference. Preserve a short faithful excerpt with its source label. Record current workaround, affected user, timing, stated impact, and contrary evidence when present.

De-duplicate before counting. Multiple tickets, notes, or reviews from one person are one demand source unless I can establish independent users. Use one frequency label only:
- Known: [n] independent sources in this input set
- Known: repeated contacts from [one source / n sources]
- Unknown: no independent count is available
Never invent frequency.

Return a Feedback Map with one row per theme and these columns:
- Theme (state the user problem, not a feature)
- Direct evidence (source label + short excerpt)
- Affected user
- Frequency when known
- Severity (blocked, delayed, or inconvenient, with evidence)
- Current workaround
- Contrary evidence / uncertainty
- Recommendation: keep, watch, test, or decline
- Owner check required

Recommendation rules:
- Keep: retain an evidence-backed theme for my product discussion; it does not authorize work.
- Watch: preserve the signal and name the evidence that is missing.
- Test: propose one small, reversible learning step and its success condition; do not draft it until I approve.
- Decline: record why the request is one-off, out of scope, unsupported, or outweighed by contrary evidence.

Run this red-flag pass before showing the map:
- Do not count duplicates as independent demand.
- Do not treat sentiment as willingness to pay.
- Do not invent frequency, severity, or impact.
- Do not mistake one enterprise request for a market.
- Do not skip contrary evidence or uncertainty.
- Do not include customer identity where a user segment is enough.
- Do not auto-create roadmap tickets or autonomous product changes.

Finish with: strongest evidence, weakest assumption, contrary evidence, and the one product decision I must make. Ask for my approval before drafting a ticket, experiment plan, product brief, or consequential follow-on work.
Use only feedback you are authorized to review for this specific decision.
Keep out
  • Private messages without authority or credentials.
  • Health, legal, HR, or other sensitive details.
  • Customer names when a user segment is enough.
  • Copied reviews and repeat contacts counted as demand.
  • Assumed willingness to pay or invented severity.

The problem

A loud request can distort a quiet pattern.

One enterprise customer may ask for an integration in every call. Three separate new users may quietly describe the same setup failure. Those are different signals.

The useful move is to preserve the direct evidence, group the problems, show what does not fit, and leave the product choice with the owner. GDS describes this kind of analysis as sorting observations into themes and using findings to decide what to work on, change, or research next.1

Map the problem. Keep the uncertainty. Decide with your team.

The map is a decision record, not a feature queue.

Feedback becomes useful when the team can see who is affected, what they actually said, what they do now, and how much remains unknown. A short finding with its essential facts and consequence is easier to review in a roadmap conversation than a pile of quotes.2

Use the smallest set that can answer the decision.

State the decision before loading evidence. That keeps a roadmap conversation from becoming a request dump. Data minimisation guidance makes the same practical point for personal data: use what is relevant and necessary for the stated purpose, no more.3

Ingredient 1

A decision

Choose one: a next improvement, a roadmap discussion, or an onboarding investigation.

Ingredient 2

Approved source set

Use a fixed date range and a known group of interview notes, support themes, review text, or survey responses.

Ingredient 3

Source labels

Keep a neutral label, date, channel, and duplicate status so the evidence can be reviewed.

Ingredient 4

Constraints

Name the affected user segment when needed and any product boundary that makes a request out of scope.

  • Private messages without authority. A chat thread is not available just because it contains a product opinion.
  • Credentials and sensitive details. Remove health, legal, HR, financial, and other information that does not answer the product question.
  • Customer identity by default. Keep the user segment; keep a name only when it materially changes the decision.
  • Unbounded archives. Start with one defined research round or time window, not the full history.

The recipe

Name the product decision.

Write the decision in one line. If the team needs a new checkout flow, do not also ask the map to settle pricing, expansion, and retention.

Normalize each observation.

Capture the direct wording, neutral source label, user moment, stated impact, current workaround, and date when known. Keep interpretation in its own field.

De-duplicate before frequency.

Three tickets from one person are operationally important but one independent demand source. Make that visible.

Cluster problems, then test the cluster.

Group by the user problem or journey point. Keep one-off items, contrary evidence, and unknowns instead of forcing a clean theme.

Complete the Feedback Map.

Every theme gets evidence, affected user, frequency when known, severity with reason, workaround, uncertainty, a recommendation, and an owner check.

Stop for the owner decision.

Discuss the map. Only after approval may someone draft a ticket, experiment plan, or product brief. The map never creates those on its own.

Map rule

State the problem before the solution. Give direct evidence and uncertainty equal visibility. Recommendations are review options, not commands.

Run the taste test before the map influences work.

NIST’s AI Risk Management Framework calls for defining the task, documenting data selection and limits, and documenting human oversight. Those are useful constraints for a smaller feedback-analysis workflow too.4

TraceableCan the owner find direct evidence behind every theme?
De-duplicatedAre repeat contacts separated from independent sources?
SpecificDoes the theme name a user problem instead of a requested feature?
CalibratedIs frequency known, unknown, or one source without guesswork?
Contrary evidenceDoes the map show what conflicts with the pattern or remains missing?
Decision-readyIs the owner check clear without a hidden roadmap commitment?
Stop condition

Do not use the map to prioritize work if direct evidence is untraceable, duplicate status is unclear, the input is not authorized, or the recommendation hides a material unknown.

Start with one decision you can review this week.

Pick a five-to-fifteen-item input set you are allowed to inspect. Map the evidence. Take the map into the next product conversation. Keep the method if it makes the discussion sharper; change the fields if the owner keeps needing a fact that is absent.
